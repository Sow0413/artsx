# 測量

手軽に観測、手軽に測設。いつでも何処でも、測って出せる。

iPhone / iPad 向けの測量アプリです。地図タブ、図面タブ、作業ごとの精度の色、三角点での検証、取った点の引き継ぎ、受取手向けの書き出しが動きます。

## iPad の Swift Playgrounds で開く

Mac も Apple Developer の登録も要りません。iPadOS 17 以降の Swift Playgrounds で、自分の iPad 上で実行します。

1. `測量.swiftpm.zip` を iPad に渡す。AirDrop、iCloud Drive、メールのどれでもよい。
2. ファイル App で zip をタップして展開する。
3. 出てきた `測量.swiftpm` をタップする。Swift Playgrounds で開く。開かなければ、共有から Swift Playgrounds を選ぶ。
4. 右上の実行で起動し、位置情報を許可する。

地図の地理院タイルは、最初の表示と範囲の保存に通信が要る。見本の基準点は同梱してある。カメラの利用目的は書いてあるが、撮影画面はまだない。

ソースを直したあとは `scripts/refresh-playground.sh` を実行し、`測量.swiftpm` を zip し直す。

## 今できること

- 地図に現在地と精度の円を出す。機器がつながると段階を上げ、解が落ちたら測位は止めずに1段下げる。下がった回はバッジを黄色にして知らせる。バッジには FIX / FLOAT / 単独 / CLAS を常に文字で出す。
- 地図の上で作業を切り替える。精度バッジの色は、今の精度が今の作業の要求を満たすかで決まる。
- 要求精度と、楽観的な報告にかける係数は「数値」から直せる。SitePack の JSON に残る。
- 国土地理院の標準地図を重ねる。見たタイルは端末に残り、表示中の範囲は「この範囲を保存」で圏外用に取っておける。
- 近くの基準点を地図に出し、同じ点を既定3回置く。各回の平均とずれ、回ごとの差、全体の平均、収束の線を出す。そろっていれば補正値にして、以後の観測から引く。作業の最後にもう一度置くと、戻り点検になる。
- 測るタブと地図から、今の作業で点を残す。点名は頭のアルファベットと連番（T1、T2）。頭文字は記録ごとに残り、座標簿にある名前は飛ばす。下見の点は捨てず、作業種別と取得時の精度を残したまま、あとから測量点の座標に乗せ替えられる。
- 基準点は段階2の RTK FIX のあいだだけ記録できる。FLOAT と単独、iPhone の GPS は残せない。解が落ちて段階が下がったら記録だけ止め、測位は続ける。FIX が切れたら秒数はやり直す。
- 点ごとに観測状況を残す。解、衛星数と系統、PDOP、水平と高さ、補正の遅れと補正元、観測時刻・秒数・エポック、機器。測るタブと出来形の帳票に出す。iPhone には衛星数・PDOP・補正の遅れが無い。
- 下のタブは 地図 / 図面 / 測る / 出す / オペ。出すは、絞った座標簿を SIMA、座標一覧 CSV、DXF、SFC、出来形管理表 PDF にする。点群と 3D は点群フォルダに保存するだけで、既定の出力には入れない。
- 路線では、図面の線か、No.23 のような測点名の点列を中心線にする。追加距離を張り、現在地を「No.23+5.0m 左 3.2m」と 0.1m で大きく出す。間隔は既定 20m で変えられ、起点の No. も指定できる。iPhone の精度で足りる。中心線は project.json に残り、あとから他の端末へ渡せば同じ測点を出せる。位置の送信そのものはまだない。
- オペ画面は運転席向け。測点と左右、中心線に対する大きな矢印（進行方向、無ければ端末の方位）、下がり、目標までの作業半径を出す。下がりは 0.1m。計画高（床掘底）があれば「下がり 1.8m」、無ければ高さそのもの。iPhone の値をそのまま使い、参考の注記は小さく添える。端末を目の高さで持つときは今の高さから計画高を引く。地盤か機体に置くときは視線高（既定 2.0m）を足す。画面はスリープせず、横でも読める。精度の色だけ小さく出す。下に「押して話す」がある。チャンネルは開いているプロジェクト。測点を添えるかは切り替えられ、発話はプロジェクトの `無線.json` に残る。
- 無線は半二重。中継は現場の P510 に置く小さなサーバーを想定し、この版は差し込み口とスタブ、仕様 `docs/ptt.md` まで。届かないときは同じプロジェクトの近くの端末へ MultipeerConnectivity（サービス名 `survey-ptt`）で渡す。どちらも無理なら端末内の記録だけ。iOS アプリは PushToTalk を呼ぶ。Playgrounds は `SURVEY_PLAYGROUND` でその権限を切る。実機の送受信、APNs、マイク、Bluetooth の発見は未確認。
- インシデントと接近は、共通の列 `incident-stat/1`（作業種類、時間帯、天候、距離、重機種類、役割）にそろえて集計する。地図の「統計」で、このプロジェクトのヒートマップと、作業別・時間帯別の件数を出す。個人名は役割だけにできる。書き出す `記録簿/統計.csv` は派生ファイルで、確定した記録は変えない。全プロジェクトの月次 PDF と地図は `tools/p510/aggregate_incidents.py`（CSV または SQLite）。P510 のサーバーそのものは無い。
- 接近警報が鳴ったとき、または「ヒヤリ」を押したとき（オペ画面、地図、図面、Apple Watch、Siri）に、インシデントを作る。中身は日時、関係者の座標・測点・向き・距離、前後60秒の軌跡、重機の作業半径、そのときの作業（記録種類と名前）、位置を重ねた図面と地図の PNG、精度と段階、PTT の記録と読み上げ、任意の写真と音声メモ。開始から60秒後に一度だけ確定し、`記録簿/インシデント/` に日本語のヒヤリハット報告書 PDF を置く。確定した記録は書き換えない。P510 が届くときはその口へ渡し、届かないあいだは端末に残す。図面と地図の PNG は座標の切り出しで、CAD 画面や地理院タイルの撮影ではない。Watch、Siri、写真、音声メモ、P510 への送信は未確認。
- 同じプロジェクトの端末は、位置と役割（重機 / 作業員）を交換する。圏内は P510 の中継、圏外は同じ近距離の口。UWB（Nearby Interaction）が使える端末は、その距離を GNSS より優先する。地図・図面・オペ画面に相手と、重機の作業半径の円を出す。オペ画面では距離より方向を先に出す。基準は、動いていれば進行方向、止まっていればコンパス。縁の矢印は近いほど大きく赤い。重機からは人を「右うしろ 12.0m」、作業員からは重機を同じ言い方で出す。作業半径の手前（既定は半径＋10m、変更可）では、向きが取れていれば自動で日本語の声を出す。重機は「右うしろ、人、15メートル」、作業員は「重機に近づいています、左前」。同じ相手には既定 30 秒あけ、1m 以上近づいたらその前にもう一度言う。読み上げは止めず、イヤホンと車の Bluetooth にも流す。声のあと、その相手へワンタップで話す大きなボタンを出す。方向が変わったときの読み上げは任意で、既定はオフ。人が作業半径＋余裕（既定 +5m、変更可）に入ると、両方で音・振動・画面赤。注意の距離（既定 50m、変更可）以内は黄。接近はプロジェクトの `接近.json` に残る。画面には「補助。安全確認の代わりではない」と出す。Apple Watch へ振動の合図を送るソースはある。実機の位置共有、UWB、Watch の振動は未確認。Playgrounds では UWB と Watch の権限を切る。
- 作業半径は機種の目安（20t は約 9m）か手入力で、project.json に残す。地図と図面に現在地中心の円を描き、タップした目標点と掘削範囲（掘削・床掘・法面、または設計の閉じた線）が半径の内か外かを色で出す。オペ画面は「目標まで 12.3m（半径外 3.3m）」のように 0.1m で出す。マシンガイダンスではない。
- 都道府県は project.json に残す。告示の対応で、県が一つの系ならその系に決める。北海道・東京都・鹿児島県・沖縄県は複数の系を候補に残す。県が無ければ現在地で絞る。
- 座標簿は点名の頭文字、種類、出典、解段階、水平精度、取込日、地図で囲んだ範囲で同時に絞れる。書き出すのは絞った点だけ。
- 図面タブで DXF と SFC（SXF Ver.2/3 のテキスト）を開く。拡大・回転、背景と設計の表示切替、現在地と精度の色、交点・端点・点への測設。平面直角座標の 1〜19 系で地理院タイルに重ね、系が現在地から大きく外れたら候補を出す。
- 図面の点と、地図・現在地・座標簿の点を 2 組以上対応づけ、移動・回転・縮尺の相似変換を最小二乗で求める。3 組以上は点ごとの残差。縮尺を 1 に固定できる。系番号が不明でも、対応点から合いそうな系を出す。
- 合わせは名前と版を付けて `設計/合わせ/` に置く。元の DXF は変えない。地図や現在地だけで合わせたものには「地図並み（m）」と、測設では座標簿で合わせ直す札を付ける。
- プロジェクトは `SitePack/プロジェクト/名前/` 。下に 座標簿、記録（日付_種類_名前 と record.json）、点群、設計、下敷き、出す。インシデントは作ったときに `記録簿/インシデント/` を足す。`project.json` が案件の札。
- 座標、精度の判定、平面直角の換算、DXF、合わせ、タイル、検証の統計は `SurveyCore` にあり、Linux で `swift test` できる。

## まだできないこと

- CLAS と RTK の受信機はつながない。段階の上げ下げは、位置の型が報告した機器と解で決める。
- 出来形管理表 PDF の日本語は、HeiseiKakuGo-W5 を参照しているだけでフォントは埋め込んでいない。端末にそのフォントが無いと日本語のページは出ない。ASCII の表は残る。地理院ベクトルとの照合は、取れたタイルの線と背景を比べるところまで。通信が無いと照合できない。
- バイナリ DXF、SPLINE、ELLIPSE、HATCH、寸法、引出線、イメージ、3DFACE は読まない。読めなかった種類は数だけ出す。ブロックは中の線・円・文字を展開する。動的ブロックと属性は展開しない。
- 地点と軌跡の型はある。画面に出す記録は、作業で残した点だけ。
- 全国の三角点台帳は入っていない。同梱は見本だけ。
- 地理院タイルはアプリに同梱しない。最初の表示と、範囲の保存には通信が要る。
- この環境には Xcode がない。iOS アプリ本体も、Playgrounds のパッケージも、ここではビルドしていない。オペ画面の下がりは数値だけ。カメラ映像への計画高の重ねはまだない。PTT の実機部分（PushToTalk、APNs、マイク、MultipeerConnectivity）は未確認。P510 の中継プロセスは無い。接近の実機部分（位置の交換、UWB、Apple Watch の振動、音、読み上げ）も未確認。インシデントの Watch ボタン、Siri、写真、音声メモ、図面の実画面の切り出し、地理院の地図画像、P510 への送信も未確認。

## 精度の色

バッジの色は、今の水平・高さの精度が、今の作業の要求以内かどうかで決まる。同じ iPhone の値でも、下見なら緑、丁張なら赤になる。

| 色 | 意味 |
| --- | --- |
| 緑 | 実効精度が、水平も高さも要求以内 |
| 黄 | 要求は外れるが、2倍以内。高さが未取得のときも黄 |
| 赤 | 2倍より粗い |
| 灰色 | 位置がない、許可がない、水平精度が数値になっていない |

実効精度は、報告値に安全側の係数をかけた値。三角点の検証でその機器と補正が楽観的だったときだけ、係数は 1 より大きくなる。既定は 2。かけていないときは 1。

足りないときは「あと何 cm 足りないか」と、届く手段を出す。手段の目安は仮で、設定には出さない。三角点補正 0.50m／0.50m、CLAS 0.05m／0.10m、RTK 0.02m／0.03m、TS 0.005m／0.005m。水平と高さの両方が要求以内の手段だけ出す。丁張（2cm／1cm）に届くのは TS だけ。

測設に使ってよいかは、色とは別に見る。外部受信機の RTK Fix で、かつ色が緑のときだけ。iPhone や CLAS が下見で緑でも、測設の合格にはしない。

見本の iPhone（水平 約3m、高さ 8m）は、下見の高さ 5m に対して 2倍以内なので黄になる。水平 3.2m・高さ 4m の同じ端末は、下見で緑、丁張で赤。

三角点補正が有効なあいだは、その機器の判定を、ばらつきと目安 0.50m の粗い方で見る。概略なら緑になり、丁張は赤のまま。補正が古い、または別の機器のときは、報告の精度のまま判定する。

作業の仮の既定値は次のとおり。高さは、丁張だけ 1cm。ほかは水平と同じ。

| 作業 | 水平 | 高さ |
| --- | --- | --- |
| 下見・現況スケッチ | 5m | 5m |
| 概略の位置出し | 0.5m | 0.5m |
| 測量（トラバー） | 0.02m | 0.02m |
| 丁張・測設 | 0.02m | 0.01m |
| 出来形 | 0.05m | 0.05m |
| 境界・基準点 | 0.02m | 0.02m |

地図上部の「数値」で直す。保存先は Application Support の `SitePack/work-requirements.json`。楽観的だった機器は `SitePack/instrument-trust.json`。測地系の選択はない。

内部の段階は 0 が iPhone、1 が CLAS、2 が RTK、3 が併用。今つながるのは段階0だけ。

## 座標

端末の中は WGS84/ITRF の緯度、経度、楕円体高。画面下の注記は「JGD2024・下見／概略用」。測地系の変換は、出すときの一度だけにする。

取った点は `SitePack/field-observations.json`。`captured` が取得時の位置と精度、`adopted` が乗せ替えた測量点の座標。補正を引いた座標は `corrected`、戻り点検で割り振った座標は `closureAdjustment`。どれも `captured` は消さない。要再測は印だけ付ける。

## 図面

DXF は ASCII。文字コードは `$DWGCODEPAGE` を見て、日本の CAD の Shift_JIS（ANSI_932）と UTF-8 を読む。対応する図形は LINE、LWPOLYLINE、POLYLINE、CIRCLE、ARC、TEXT、MTEXT、POINT、INSERT。レイヤと色（ACI と真色）を読む。バルジは円弧として割る。INSERT はブロックの中身を展開する。GPL の DXF ライブラリは使っていない。

SFC は SXF Ver.2 と Ver.3 のテキスト。`/*SXF … SXF*/` の中のレイヤ、線、折線、円、円弧、文字、点を読む。レイヤ名に地形・背景・BGD・2500 などが入るものは背景、ほかは設計。文字コードは UTF-8、ダメなら Shift_JIS。公共座標の数値はそのままなので、系を選べば地図に載る。寸法、楕円、ハッチング、複合曲線、記号は数だけ数えて描かない。原本のバイト列は変えない。

図面の画面は SwiftUI の Canvas。見えている範囲だけ、格子の索引から拾って描く。ピンチで拡大、ドラッグで移動、回転ジェスチャーと 90° ボタンで回す。レイヤは一覧で出す・消す。背景と設計は、別にまとめて出せる。

平面直角座標は 1〜19 系。換算は国土地理院が公開しているガウス・クリューゲルの級数（河瀬 2011）で、SurveyCore に一つだけ置く。X は北、Y は東、原点は 0、X 軸上の縮尺は 0.9999。500 km を足す偽の東距は加えない。楕円体は GRS80。緯度経度から平面へ、平面から緯度経度へ、両方ある。

系を選んで地理院タイルの上に線を重ねる。図面の中央をその系で読んだ位置が、現在地から 20 km より遠いときは警告し、近くに載る系を候補にする。ファイルの X を東とみるか北とみるかも切り替える。

手合わせは、図面の点と緯度経度（地図のタップ、現在地、座標簿）を 2 組以上結ぶ。選んだ系の東・北に直してから、移動・回転・縮尺の相似変換を最小二乗で求める。縮尺を 1 に固定できる。3 組以上は点ごとの残差と、残差の二乗平均を出す。対応点の数値がどれかの系の公共座標と 500 m 以内でそろうときは、その系を候補にする。そろわないときは、その場所の原点に近い系を候補にする。図面が現場のローカル座標でも、系の取り違えとは分けて出す。

合わせの結果は `設計/合わせ/名前/v1.json` のように版を足す。受け取った DXF のバイト列は `設計/` にそのまま残し、系と軸は `設計/名前.変換.json` に書く。地図または現在地が対応点に含まれる合わせは精度の札を「地図並み（m）」にし、「測設では座標簿の点で合わせ直してください。」を添える。対応点がすべて座標簿のときは札を「座標簿」にする。

現在地は、同じ換算で図面の座標に戻して点と精度の円にする。色は上の精度バッジと同じ。図面をタップすると、交点・端点・点のうちいちばん近いものに吸いつく。図面の X Y、その系の東と北、緯度経度、現在地からの測地線距離と北からの方位を出す。cm で出すのは、座標簿の点だけで合わせた図面のときだけ。地図並みの合わせや、そのまま載せた SFC はメートル。

背景の照合は、地理院のベクトルタイル（道路縁、建物外周、水涯線、海岸線など）を自前で読んで、同じ系の平面に置く。背景の線の中央値が 2 m 以内で、6割以上が 5 m 以内なら「座標あり・そのまま使える」。ずれていれば、移動の距離と北からの方位を出し、縮尺を 1 に固定した ICP で合わせる案を保存できる。その札は地図並み（m）。線が合わない図面は、合わないと出して手合わせに残す。軸は東西南北の両読みを試し、よく合う方を勧める。通信できないときは照合しない。

プロジェクトの置き場所は Application Support の `SitePack/プロジェクト/名前/`。中は `座標簿/`、`記録/日付_種類_名前/record.json`、`点群/`、`設計/`、`下敷き/`、`出す/`、と `project.json`。

## 三角点で検証

iPhone を、座標が分かっている三角点の上に置く。地図の三角印をタップし、回数は 1・3・5 から選ぶ（既定は3回）。1回ごとに置き直し、向きを変える。長さは1分・10分・30分（既定は10分）。1秒に1点、緯度経度と水平・高さの精度を残す。

回が終わるたびに、その回の平均とずれを足す。全部終わると、回ごとの差（再現性）と全体の平均を一覧にする。各回の線は、置いてからの経過時間に対する累積平均のずれで、水平と高さを描く。60秒のあいだの変化が水平・高さとも 2cm 以下になって、以後もそうなら、その時刻を「落ち着いた」とする。

回が2回以上で、平均のばらつきが水平 2m・高さ 3m 以下なら「この三角点で補正」を押せる。平均のずれを `SitePack/control-corrections.json` に残し、同じ機器の以後の観測から引く。取得時刻と経過分は常に出す。2時間を超えると黄色になり、判定にも座標にも使わない。高さの補正は、楕円体高どうしで比べられたときだけ。

作業の最後に同じ三角点へ戻って記録すると、始めの補正との差を出す。水平・高さとも 0.5m 以内なら「補正有効」。超えたら、途中の点へ時刻の割合で差を割り振るか、要再測の印を付ける。元の座標は残し、割り振った座標と印は別に持つ。

1回の中身は次のとおり。

- 平均位置。既知点を原点にした東西・南北の平均で、GRS80 の Vincenty 測地線から戻す。
- 水平の差。平均位置と既知点の測地線距離。
- 高さの差。既知の高さも楕円体高のときだけ、精度の判定に使う。成果が標高のときは、楕円体高から標高を引いた値を出す。ジオイドが含まれるので、楽観かどうかは判定しない。
- ばらつき。東西・南北の標本標準偏差を合成した値と、平均位置からの距離の95%。
- 報告精度。水平精度の平均が、平均位置の実際のずれより小さいとき「楽観的」。あわせて、68%の円（iPhone の `horizontalAccuracy`）の外に出た点の数。

CSV は記録の各行と、先頭の summary 行。共有シートから書き出す。

距離は GRS80（赤道半径 6378137 m、扁平率の逆数 298.257222101）の Vincenty。対蹠点で収束しないときはその点を捨てる。Karney の式は対蹠点向けなので、ここには移植していない。カメラの追従だけは、これまで通り球面の近似を使う。

見本は `SurveyApp/Resources/sample-control-points.json`（同じ内容の CSV もある）。日本経緯度原点の緯度経度と日本水準原点の標高は測量法施行令の値。富士山は公表されている緯度経度と令和7年の標高。机上の見本点は実在しない。全国の成果表は同梱しない。測量成果の複製には承認が要ることがある。

現場パックは、アプリの Application Support にある `SitePack/control-points.json`（無ければ `control-points.csv`）。`fgd_points.sqlite` から自分で切り出したファイルを、この形で置く。JSON の点は `id`、`name`、`kind`、`grade`、`latitudeDegrees`、`longitudeDegrees`、`heightMeters`、`heightKind`（`ellipsoidal` / `orthometric` / `unspecified`）、任意の `ellipsoidalHeightMeters`、`sourceNote`。楕円体高が入っていれば、高さの判定にそれを使う。ファイルが無いときは見本に戻る。

## 地図タブの参考

UX は **ジオグラフィカ（Geographica）** をモデルにした。株式会社エヌ・シィ・ティの日本向け地図アプリで、範囲を指定して地理院タイルを先に保存する、現在地を大きく出す、地点と軌跡を扱う、という使い方を借りている。コードは使っていない。

オフラインタイルの保存と、iOS で速く描く構成は **Organic Maps**（Apache-2.0）を参考にした。地域をひとまとまりにする、手元のデータを通信より先に見る、短いメモリキャッシュを置く、描画と保存を分ける、という考え方だけを Swift で書き直している。C++ と OpenGL の実装は移植していない。M0 の描画は MapKit。

OsmAnd と QField は GPL。それらのコードは読んでいないし、コピーしていない。

## クラウド Mac と TestFlight

GitHub Actions（`.github/workflows/ci.yml`）は macOS 15 のランナーで、次の3つ。

1. Ubuntu で `SurveyCore` の `swift test`
2. macOS で署名なしの `xcodebuild`。API キーが無くてもここは通る
3. 手動実行で `upload_testflight` を選んだときだけ、署名して App Store Connect へ上げる。キーが無いときは何も上げず、成功扱いで終わる

署名は Xcode の自動署名（`-allowProvisioningUpdates` と App Store Connect API キー）だけ。証明書とプロファイルは、その場で作ってアーカイブに使う。キーの中身はログに出さない。

### captain が一度だけすること

メンバーシップの有効化を待つ。有効になったら、ブラウザで次を行う。

1. [App Store Connect](https://appstoreconnect.apple.com) の「ビジネス」で、有料アプリ契約に同意する。無料配信でも要る。
2. [Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources/identifiers/list) で App ID を追加する。Bundle ID は `jp.oshiro.survey`（変えるなら、その ID）。
3. App Store Connect の「アプリ」→「新規 App」。プラットフォームは iOS、名前は測量、Bundle ID は今作った ID、SKU は `survey` でよい。
4. 「ユーザとアクセス」→「統合」→ App Store Connect API でキーを作る。役割は Admin。Issuer ID と Key ID を控え、`.p8` をダウンロードする。このファイルは一度しか出ない。
5. GitHub の Settings → Secrets and variables → Actions に、下の Secret を置く。チャットや README には貼らない。
6. Actions の CI を手動実行し、`upload_testflight` をオンにする。ビルド番号は実行回数になる。

| Secret | 渡す値 |
| --- | --- |
| `ASC_ISSUER_ID` | API キーの Issuer ID（UUID） |
| `ASC_KEY_ID` | API キーの Key ID（10文字） |
| `ASC_KEY_P8` | `.p8` の中身。`BEGIN PRIVATE KEY` から終わりまで。改行の代わりに `\n` でも、Base64 1行でもよい |
| `ASC_TEAM_ID` | 任意。チームが複数あるときだけ、10文字の Team ID |

Variable `BUNDLE_ID` と `MARKETING_VERSION` は任意。空なら `jp.oshiro.survey` と `0.1.0`。

iPad の Playgrounds 用 ID `jp.captain.survey.playground` は、この配信 ID とは別のまま。
